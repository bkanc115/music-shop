# Правила внесения изменений

## Модель ветвления (GitFlow)

- `main` — стабильные релизные версии. Каждая версия помечается тегом `vX.Y.Z`.
- `develop` — основная ветка интеграции новых функций.
- `feature/<номер-задачи>-<краткое-имя>` — ветка разработки одной функции, создаётся от
`develop`.
- `release/<X.Y.Z>` — ветка подготовки релиза от `develop`, сливается в `main` (с тегом)
и обратно в `develop`.
- `hotfix/<X.Y.Z>` — срочное исправление от `main`, сливается в `main` и `develop`.

## Порядок внесения изменений

1. Создать задачу (Issue) на GitHub с описанием цели и критериев готовности.
2. Создать ветку от актуального `develop`: `git switch -c feature/<id>-<slug>`.
3. Вносить изменения осмысленными атомарными коммитами (формат: `feat:`, `fix:`, `docs:`,
`chore:`).
4. Выполнить обязательные локальные проверки (`make verify`) до отправки PR.
5. Открыть Pull Request в `develop`, указать связанную задачу (`Closes #<id>`).
6. Проверить изменения (особенно критические файлы приёмки) и выполнить слияние через
merge commit.

## Обязательные команды локальной проверки

- `make setup` — первоначальная настройка окружения
- `make run` — локальный запуск приложения
- `make verify` — полный набор обязательных проверок проекта 

## Запрещённые действия

- Прямая отправка коммитов (`push`) в `main` и `develop` в обход Pull Request.
- Добавление в репозиторий паролей, токенов, `.env`, ключей и локальных файлов (`.venv`,
`logs`).
- Удаление тестов, отключение анализаторов, снижение порогов качества и ослабление CI
ради прохождения проверки.
- Изменение критических файлов приёмки (`Makefile`, тесты, конфигурации проверок и CI)
без явного отображения и отдельной проверки в Pull Request.

## Порядок приёмки

Изменение принимается только если:
- связана задача (Issue) и соблюдены правила ветвления GitFlow;
- локальные проверки (`make verify`) прошли без ошибок;
- приложение запускается, `/health` отвечает `200 OK`, ошибки логируются, секреты не
попали в дифф.
